# Spec: `bespoke` CLI

The only supported way to create, run, deploy, and operate apps. Agents and
humans alike use it (the [Justfile](../../Justfile) recipes wrap it);
hand-editing generated artifacts (Caddy routes, systemd units, Litestream
config) is forbidden by convention. Source: `cmd/bespoke`.

## Commands

### `bespoke new <slug>`

1. Validate `slug` against the [manifest spec](app-manifest.md) and
   uniqueness; `platformd` is reserved. Exit non-zero without side effects on
   any validation failure.
2. Scaffold `apps/<slug>/` in the canonical shape: `app.toml`, `main.go`
   (db + web.Run wiring), `views/home.templ` (AppShell + Card),
   `migrations/0001_init.sql`.
3. Assign the next free port (sequential from 4101, max 4999) into `app.toml`.
4. Append `/<slug>` to `.gitignore` (idempotent) so a direct
   `go build ./apps/<slug>` can never leave a committable binary in the
   repo root.
5. Run `templ generate` for the new view if `tools/templ` is installed, so
   the app compiles immediately; otherwise print the setup commands.

### `bespoke dev`

Run platformd plus **every** manifest app locally on `127.0.0.1`, each with
`BESPOKE_DEV_USER` set (default `<username>@local`). The process list comes
from the registry — new apps join without configuration. Ctrl-C stops
everything (process-group signals).

### `bespoke gen`

Regenerate all derived artifacts into `dist/gen/` from the manifests.
Requires `deploy/deploy.env` (domain, hosts) — a fresh clone must copy
`deploy.env.example` first:

| Artifact | Content |
| --- | --- |
| `dist/gen/units/bespoke-<slug>.service` | systemd user unit per app + platformd + litestream; the platformd unit additionally sets `BESPOKE_ROOT`, a PATH including `~/.local/bin` (so the gateway can exec `copilot`), and `-internal <bind-ip>:4001` for the services plane |
| `dist/gen/bespoke.caddy` | edge route file: wildcard TLS, tailscale_auth, header stripping, subdomain→port map (label index computed from the domain depth) |
| `dist/gen/litestream.yml` | replication entry per app database |

Every artifact starts with `# GENERATED by bespoke — do not edit`.

### `bespoke deploy [slug…|--all] [--edge] [--no-wait]`

Runs on the dev machine (or the app host itself, for spooled deploys —
ADR-0023); remote hosts per
[ADR-0011](../adr/0011-split-host-deployment.md). platformd always deploys
(its registry view must match the shipped manifests). With no slugs (or
`--all`) every app deploys. Any manifest warning aborts the deploy before
side effects ("fix manifest warnings before deploying"; `new` has the same
guard).

1. Regenerate artifacts (`gen`).
2. Cross-compile each target with `CGO_ENABLED=0 GOOS=linux GOARCH=<deploy.env>`;
   `platformd`, `bespoke`, and `builder-runner` always build.
3. rsync binaries to a staging dir (`~/bespoke/bin.new/`), manifests, units,
   and litestream config to the app host; create `~/bespoke/env` if missing
   with `BESPOKE_BIND_IP`, `BESPOKE_DOMAIN`,
   `BESPOKE_LLM_URL=http://<selfie-ts-ip>:4001`, `BESPOKE_ROOT`, and
   `BESPOKE_LEMONADE_URL=http://127.0.0.1:13305/api/v1`.
4. If the host is bootstrapped for the builder plane (`/var/lib/bespoke/bin`
   exists): move `bespoke` + `builder-runner` there and
   `enable --now bespoke-deploywatch.path`. Skipped silently otherwise.
5. **Quiesce (ADR-0023):** unless `--no-wait`, poll `GET /llm/activity` on
   the 4001 plane (over ssh — the ACL blocks it remotely) until
   `inflight == 0`, up to 180s, so restarts never kill an in-flight
   completion. An unreachable gateway proceeds immediately.
6. Per app: keep the old binary as `.prev`, swap in the new one,
   `daemon-reload` + `enable --now` + restart the unit (a brand-new app
   starts with no manual step), then poll
   `http://<selfie-ts-ip>:<port>/healthz` — 20 attempts, 1s curl timeout,
   0.5s spacing (≈10–30s wall clock); on failure restore `.prev`, restart,
   exit non-zero.
7. `--edge`: push `dist/gen/bespoke.caddy` to the edge host (sudo tee) and
   reload Caddy. Required on first deploy and whenever apps are added or
   removed.

### `bespoke deploywatch`

Not for interactive use: the deploy-spool drain run by the generated
`bespoke-deploywatch.path` unit on the app host (ADR-0023,
[builder-plane.md](../design/builder-plane.md)). Per request: archive the
request, verify + fast-forward the run's git bundle into the canonical
clone (`~/bespoke/repo`), `just check`, push `main`, then the narrow
`bespoke deploy <slug> --edge`; outcome written to
`runs/<run>/deploy.json`. A bundle that fails any step rolls the clone
back and deploys nothing.

### `bespoke list [--json]`

Registry dump from the manifests. `--json` is the stable agent-facing form:
`{"apps": [...], "warnings": [...]}`.

### `bespoke logs <slug> [-f]`

`ssh -t <app host> journalctl --user -u bespoke-<slug> -n 100 [-f]`.

### `bespoke rm <slug> [--force]`

Remote (best-effort, continues on failure): stop + disable the unit, remove
the unit file, the binary and its `.prev`, and the shipped
`~/bespoke/apps/<slug>/` manifest dir; archive `~/bespoke/data/<slug>.db`
to `data/archive/`. Local: deletes `apps/<slug>/` only with `--force`. Never
deletes a database anywhere. Prints the reminder to run
`bespoke deploy --all --edge` to drop the route.

## Behavior contract

- Idempotent: re-running any command converges to the same state.
- All generated artifacts carry the GENERATED header.
- ssh calls use a connect timeout so unreachable hosts fail fast instead of
  hanging (exception: the interactive `logs` session).
- `--json` output is stable; it is the agent-facing API.
