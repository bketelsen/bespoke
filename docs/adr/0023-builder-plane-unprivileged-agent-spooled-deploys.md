# 0023 — Builder plane: unprivileged agent user, spooled deploys

- **Status:** Accepted
- **Date:** 2026-08-02

## Context

Phase 6 is complete (three consecutive one-shot apps, the third by a
different agent), which unparks the roadmap's **builder app**: type "build
me a…" on the dashboard, watch an agentic session spec, build, test, and
deploy a new app. The roadmap sketch assumed "the LLM gateway grows the
opt-in agentic session type ADR-0009 deferred." Facts on the ground:

- Copilot SDK tool execution (shell, file edits) happens **inside the
  Copilot CLI process**. platformd's CLI runs as the platform user (`bjk`),
  who owns every prod database, binary, and systemd user unit on the app
  host. An agentic session hosted by platformd would run shell as that user.
- The app host runs everything as systemd `--user` units under `bjk`
  (linger enabled); there are no root units and no passwordless sudo.
  Routine deploys are pure ssh/rsync + `systemctl --user`
  ([ADR-0011](0011-split-host-deployment.md)).
- `bespoke deploy` restarts **platformd unconditionally on every deploy**,
  and restarts each targeted app unit. Restarting an app or platformd kills
  any in-flight LLM completion (a family member mid-chat loses the reply).
- A process that triggers a deploy of itself dies mid-deploy: the deploy
  script runs inside the caller's cgroup and `systemctl --user restart`
  kills the cgroup.
- The Tailscale ACL opens app-host ports 4000–4999 to the edge host only;
  ports outside that window are unreachable from anywhere but the host
  itself.
- ADR-0011 states "the app host needs no Go toolchain — it only ever
  receives binaries."

## Decision

The builder's agentic sessions run **outside the gateway, as an
unprivileged peer unix user**; all hand-offs between trust domains are
**spooled files**; deploys are executed and verified only by the platform
side. Concretely:

1. **The gateway stays inference-only.** ADR-0009's lockdown and
   ADR-0021's app-tools opt-in are unchanged. The deferred "agentic
   session type" is *rejected* for platformd forever: tool execution
   inherits the gateway process's uid, so an agentic gateway session is a
   privilege escalation by construction.
2. **A `builder` unix user hosts the coding agent.** A small **runner**
   service in `builder`'s own user-systemd (linger enabled) owns a
   dedicated Copilot SDK client/CLI with its own GitHub auth and drives one
   agentic session per build in a fresh clone under `/home/builder`
   (per-session `WorkingDirectory`; permissions auto-approved; the repo's
   AGENTS.md and `.agents/skills` load from the working directory, giving
   the agent the same instruction surface human-driven agents use).
   Guardrails are kernel-enforced: `builder` has no sudo, no access to
   `bjk`'s user-systemd, databases, binaries, or ssh keys.
3. **Two spool directories** (setgid, shared group `bespoke`, members
   `bjk` and `builder`) carry every cross-domain hand-off:
   - **build spool:** the builder app (as `bjk`) drops a build request
     (JSON); the runner streams progress events (JSONL) and finishes by
     writing the run's git commits as a bundle. Files are the audit trail.
   - **deploy spool:** the builder app drops a deploy request; a **deploy
     watcher** — a systemd `--user` path unit + oneshot service under
     `bjk`, part of the platform, generated by `bespoke gen` like every
     other unit — picks it up outside any app's cgroup.
4. **The platform side trusts nothing the agent produced.** The watcher
   fetches the bundle into the canonical clone, re-runs `just check`,
   pushes to `main` with `bjk`'s credentials (the agent never holds push
   credentials), and runs the **narrow** `bespoke deploy <slug> --edge` —
   never `--all` — so no unrelated app unit restarts.
5. **Quiesce before restart.** The gateway gains `GET /llm/activity` on
   the 4001 plane (in-flight completion count, seconds since last
   activity). The watcher polls it and waits for idle — with a bounded
   timeout and a short grace window — before restarting anything, because
   every deploy bounces platformd. A small race window remains and is
   accepted.
6. **Sandbox test runs bind `127.0.0.1:42xxx`.** The 42xxx range is
   reserved for test instances: outside the manifest range (4101–4999),
   outside the ACL's edge window, loopback-only, with `BESPOKE_LISTEN` and
   a private `BESPOKE_DATA` overriding the manifest port and data
   directory. The app's real manifest port is assigned by `bespoke new` as
   usual but is never bound during a build.
7. **ADR-0011 is refined, not reversed:** the app host gains a build
   toolchain (Go, just, golangci-lint via Homebrew) for the watcher's
   verification and for deploys initiated on-host. Deploys from the dev
   machine continue to work unchanged.

## Consequences

- Kernel walls replace prompt discipline: a confused agent can at worst
  damage `builder`'s own home directory and its run clone. Prod databases,
  units, and credentials are unreachable by uid, not by instruction.
- The same spool pattern serves both directions; every hand-off is an
  auditable file, and a restart mid-deploy cannot kill the deploy.
- The Copilot CLI must be authenticated **twice** (once per unix user),
  each a one-time interactive login. The roadmap's open question about
  Copilot subscription terms now applies with more force: builds are
  long-running automated agent sessions.
- Every deploy still bounces platformd: open dashboard SSE streams drop
  and auto-reconnect; the quiesce guard protects in-flight LLM calls, not
  SSE connections. Accepted as sub-second cosmetic.
- One-time root bootstrap on the app host (create `builder`, shared group,
  spool dirs, linger) — a documented script run with sudo, after which
  routine operation needs no privileges anywhere.
- The builder app itself is an ordinary Bespoke app; nothing in this ADR
  changes app conventions.

## Alternatives considered

- **Agentic session type in the gateway** (the original roadmap sketch):
  rejected — tool execution would run as the platform user; no
  configuration of the SDK changes the uid it executes under.
- **Builder app spawns the agent via sudo/systemd-run:** rejected — grants
  the app exactly the privileges the wall exists to withhold.
- **Container/VM isolation (podman is present on the host):** heavier to
  keep working (images, updates, GPU/cache mounts for the CLI runtime);
  a peer unix user achieves the needed isolation on a personal tailnet.
  Revisit if the agent ever needs to run untrusted third-party code.
- **Agent pushes to GitHub directly:** rejected — credential isolation is
  the point; the platform side owns push and deploy.
- **PR-based flow instead of straight-to-main:** rejected by the owner for
  a personal repo; the spool files and git history are the audit trail.
